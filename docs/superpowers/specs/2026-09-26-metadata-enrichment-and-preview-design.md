# Album, genre and BPM for every track — and a 30-second preview you can hold to hear

Design, 2026-09-26. Three sub-projects, built in order; each ships green on `pnpm verify` and lands
as its own commits on `claude/airwave-oneshot-build`.

## What this is for

A person searches, or pastes a YouTube, SoundCloud or Spotify link, and the listing shows what the
song *is*: the real artist and who features on it, the album, the cover, the length, the genre and the
tempo — not a channel name and a video thumbnail. The recommender learns from the same genre and tempo,
so autoplay and "similar to this" get better with every track that comes through. And the listing lets
them hear thirty seconds of it: a click on the cover, or holding the pointer on the row for five
seconds, in a surface that looks like it came from the same hand as the Now Playing header.

Constraints carried through: no audio is ever taken from YouTube or Spotify streams
(`docs/PROVIDER_CAPABILITIES.md`); the player shell is generated by `make-shell.py`; UX rule IDs,
tests and `design/coverage.json` move together; the styleguide is rebuilt; open, keyless sources first.

Decisions taken with the owner: when the player is paired, the hub is the **first** search source
(iTunes fills previews and gaps; unpaired is unchanged). Hover preview starts after five seconds
**with a visible hold-fill**; click starts at once; never on touch or under reduced motion.

## What exists today (read from the code)

- Hub: adapters return `title, artistName, artworkUrl, durationMs, year`; SoundCloud adds `genre`,
  `isrc`; Spotify adds `albumName`, `previewUrl`, `isrc`. A `canonical_tracks` table
  (`migrations/0004`) already keys on `musicbrainz_recording_id` / `isrc` and stores `album_name`,
  `genres`, `tags` — but nothing fills them from a link, and it has no `bpm`, featured artists or
  artwork. A MusicBrainz adapter exists and is used only for "latest releases". Outbound HTTP goes
  through `providers/http.ts` with per-adapter host allowlists and `rate-limit-manager.ts`.
- Contracts: `Track` already has `genre, genres, tags, bpm, identity.{isrc, musicbrainzRecordingId,
  musicbrainzReleaseId, acoustid}`. `SearchResultBase` has `genre, previewUrl` but no `bpm`, `genres`
  or featured artists.
- Recommender (`packages/recommendations`): `TrackFeatures = {artist, genres, tags, album, era, band}`;
  genre and tag similarity are heavily weighted; **no tempo dimension**.
- Player shell search sheet (`index.html` ~8140–8560): sources are the companion then iTunes; never
  the hub. Rows show title, artist/album/platform, time, `.srch__bpm`; BPM is fetched lazily from
  Deezer over JSONP (`enrich()`); the artwork tile is the preview button, playing iTunes' 30-second
  clip capped at **15 s** with a countdown ring. Tested by `np/find.spec.ts`, `np/hdr.spec.ts`.
- Companion: `library.ts` reads tags with `music-metadata` (including a `bpm` tag when present);
  ffmpeg is detected by `local-helper/src/tools.ts` and may be absent.

## Sub-project 1 — the hub enrichment pipeline

### Architecture

One new module, `docker-container/src/enrichment/`, called from two places and nowhere else:

1. **On resolve/search** (`search-service.ts`): after a provider returns results, `enrich(results)`
   runs with a **200 ms budget** per response — cache hits and ISRC lookups only; anything slower is
   queued. The response goes out at once; the queue fills `canonical_tracks` and later responses hit
   the cache.
2. **On library sync** (`library/service.ts`, companion push): every new or changed track without a
   MusicBrainz id is queued.

The queue is a small SQLite-backed job table (`enrichment_jobs`: `track_key, source, attempts,
next_at`), drained by one worker at MusicBrainz's rate (1 req/s, already enforced by
`rate-limit-manager`). Idempotent; a crash re-runs at most one job.

### Matching (the only part with judgement in it)

Order, stopping at the first confident hit:

1. **ISRC** → MusicBrainz `recording?query=isrc:…` (Spotify always has it; SoundCloud for label
   releases; companion files often carry it as a tag).
2. **Existing MusicBrainz id** (companion tags) → direct lookup.
3. **Cleaned title + artist + duration**:
   - YouTube: artist from a channel named `X - Topic`; otherwise split the title on ` - `;
     pull `(feat. X)`, `ft. X`, `featuring X` into `featuredArtists`; strip `[Official Video]`,
     `(Lyrics)`, `(Audio)`, `HD`, `4K`, `Official Music Video` and the like (one regex table, unit-tested).
   - Search `recording:"title" AND artist:"artist"`; accept only when `|durationMs − mb.length| ≤ 3000`
     **and** the normalised artist matches (the domain's `normalizeArtist` already strips `feat.`).
4. No confident match → the result keeps the platform's own fields and `identity.matchConfidence = 0`.
   Nothing is guessed. The listing shows what the platform said.

Confidence is stored (`0.0–1.0`) so the UI and the recommender can weigh it.

### What a match fills

| Field | Source |
| --- | --- |
| `albumName`, `musicbrainzReleaseId`, `year` | MusicBrainz release group (first official release) |
| `artistName` + `featuredArtists[]` | MusicBrainz artist credit (joinphrase `feat.` marks features) |
| `artworkUrl` | Cover Art Archive `release-group/<id>/front-250` (falls back to the platform's) |
| `genres[]`, `tags[]` | MusicBrainz genres+tags on recording → release group → artist, weighted 3:2:1 |
| `bpm` | see below |

### Genre profile

`genres` become a weighted profile, `{ "hip hop": 0.6, "trap": 0.3, "r&b": 0.1 }`, stored as
`genre_profile TEXT` (JSON) on `canonical_tracks` beside the existing `genres` list (which stays as the
ordered keys for compatibility). Sources and weights:

| Source | Weight | Notes |
| --- | --- | --- |
| MusicBrainz genres (recording / release group / artist) | 1.0 / 0.7 / 0.4 | vote counts normalised |
| Last.fm top tags (track, then artist) | 0.8 / 0.5 | **optional**: `apiKey` in the Providers tab under a new `lastfm` provider; skipped when absent |
| SoundCloud `genre` | 0.3 | free text, one weak vote |
| The file's own genre tags (companion) | 0.6 | |

Every label is mapped onto **one fixed vocabulary**: MusicBrainz's genre list (≈ 20 parents, subgenres
beneath), via `packages/domain/src/genres.ts` — aliases (`hiphop`, `Hip-Hop`, `rap/hip-hop` → `hip hop`),
parent roll-up (a subgenre also adds 0.5 to its parent). Unknown labels go to `tags`, never to
`genres`. The recommender keeps reading `genres`/`tags`; a follow-up in sub-project 1 adds
`genreProfile` to `TrackFeatures` and uses cosine similarity when both sides have one.

### BPM

No platform supplies it. Sources, in order, first hit wins; every answer stored with its source:

1. `deezer` — `track/isrc:<ISRC>` (keyless). `bpm` of 0 = unknown, not zero.
2. `acousticbrainz` — `api/v1/<mbid>/low-level` → `rhythm.bpm` (archive; still answers for the back
   catalogue).
3. The file's tag (companion) — already read.
4. **Measured from the preview clip** — for songs that are *not* downloaded. When 1–2 miss and the
   result has a `previewUrl` (Spotify 30 s, SoundCloud when playable, iTunes' clip matched in
   sub-project 2, the hub's own library range), the hub fetches that clip — preview hosts only,
   allowlisted: `audio-ssl.itunes.apple.com`, `p.scdn.co`, `cf-media.sndcdn.com`, `cf-hls-media.sndcdn.com`
   — decodes it with the ffmpeg already in the image, and runs the same tempo estimator as
   sub-project 3 (`packages/audio-core/src/tempo.ts`, plain TypeScript, so it runs in Node and in
   the browser). Stored as `bpmSource: 'preview-analysis'` with confidence; a 30 s clip is enough
   for a tempo. No song is downloaded: the clip is decoded in memory and discarded. YouTube rows
   have no clip, so they get lookup answers only, and the row says nothing rather than guessing.
5. Sub-project 3's analysis (companion, files you own).

**Unpaired players** get the same measurement in the browser: the shell decodes the iTunes clip with
Web Audio (`decodeAudioData`) and runs `tempo.ts` bundled through the bridge, only for rows the
user has previewed or added (never the whole page — it costs CPU), and caches by title|artist as
`enrich()` does today.

A **tempo dimension** is added to the recommender: `TrackFeatures.bpm: number | null`, and in
`ranking.ts` a `tempoAffinity` term = `exp(-(|Δbpm| / 12)²)` between candidate and seed, weight
0.15, only when both known; double/half-time (`2×`, `½×`) counted at 0.7. The profile learns a
preferred tempo band from plays the same way it learns genres.

### Contracts and storage

- `SearchResultBase` += `featuredArtists: string[]`, `genres: string[]`, `genreProfile:
  Record<string, number>`, `bpm: number | null`, `bpmSource: 'tag' | 'deezer' | 'acousticbrainz' |
  'preview-analysis' | 'analysis' | null`, `identity.matchConfidence`.
- `Track` += `featuredArtists`, `genreProfile`, `bpmSource`.
- Migration `0007_enrichment.sql`: `canonical_tracks` += `featured_artists TEXT '[]'`,
  `genre_profile TEXT '{}'`, `bpm REAL`, `bpm_source TEXT`, `artwork_url TEXT`, `match_confidence
  REAL`, `enriched_at TEXT`; new `enrichment_jobs`.
- New adapters: `deezer.ts`, `acousticbrainz.ts`, `lastfm.ts` (metadata-only, `role: 'metadata'`),
  hosts allowlisted in each; `KNOWN_PROVIDERS` += `deezer`, `acousticbrainz`, `lastfm`;
  `PROVIDER_CAPABILITIES.md` rows added.
- Provider GUI: three new rows in the hub's Providers tab (Last.fm with an API-key field; the other
  two keyless, on by default, with a Disable switch).

### Errors

A source that fails marks the job `next_at = now + backoff` (1 min, 10 min, 1 h, then daily), never
blocks a response, and is reported in `/providers/usage` like the others. A 429 from MusicBrainz
pauses the whole queue for the `Retry-After`.

### Tests

- Unit: title cleaner (a table of 40 real YouTube titles → expected artist/title/features);
  vocabulary mapping; profile merge; tempo affinity; duration gate.
- Integration (`docker-container/tests/integration/enrichment.test.ts`): fixture MusicBrainz/CAA/
  Deezer/AcousticBrainz servers (the existing pattern); ISRC path, title path, no-match path,
  backoff, and that a `/search` response returns within budget while the queue fills.
- Security: new hosts pass `validateOutboundUrl`; a lookalike host is refused (existing test style).

## Sub-project 2 — the player's listing: hub first, richer rows, the 30-second preview

### Sources

In `search(q)` the chain becomes `[hubSearch (when paired), companionSearch, itunesSearch]`. Hub
results are mapped by a new `fromHub(d)` onto the shell's `track(...)` shape, carrying `al`, `art`,
`prev` (= `previewUrl` when the hub has one), `bpm`, plus new fields `feat`, `genre` (top of the
profile), `conf`. **Merge rule:** iTunes results are then fetched in parallel and used only to (a)
supply `prev` for a hub row with none, matched by normalised title+artist and duration ± 3 s, and
(b) append rows the hub did not have. A pasted link goes to the hub's `/providers/resolve` first when
paired; `resolveLink`'s chain stays as the fallback. `enrich()` (Deezer JSONP) runs only for rows
still lacking `bpm` — hub rows arrive with it.

### BPM follows the song into the queue

Adding a row from search (`srch__add`) already carries duration and BPM into the library merge
("duration/BPM carry-over"). This pass makes it visible and complete: the queue row and Now Playing
show `bpm` beside the time whenever it is known; when a row is added before its BPM has arrived, the
library entry is marked `bpmPending` and the first answer (hub, Deezer, or the preview measurement
above — which is triggered by the add itself) updates the entry and repaints the queue row in place.
Tested in `find.spec.ts` ("a song added from search shows its tempo in the queue, and a late answer
fills it in") and journey step 08.

### Row

`rowHTML` gains: the sub-line reads `Artist feat. X — Album` (features from `feat`, album from `al`);
a genre chip after the numbers (`<span class="srch__genre">`) when known; `bpm` as today. A row with
`conf < 0.5` shows the platform's own line and no chip — never a guessed album. Layout stays one
40 px line; at phone width the chip hides (`NP-CHROME` width rules already cover the sheet).

### Preview

- **Length:** the whole clip, up to 30 s (`AUDITION_MS = 30_000`); the ring's dasharray maths and
  `tick` read the constant. Sources: hub `previewUrl` (Spotify 30 s, SoundCloud when `access =
  playable`, hub library range), else iTunes; **YouTube rows have no preview** and the tile says so
  on hover (`title="No preview — opens on YouTube"`, `NP-PRIN-002`).
- **Click:** as today, starts at once; click again stops.
- **Hold:** `pointerenter` on a row with `prev` starts a 5 s timer and sets `.is-arming` on the tile;
  the ring fills from 0 to 1 over those 5 s (CSS transition on `--p`, `transition: stroke-dashoffset
  5s linear`); `pointerleave`, a key press, scrolling the list, or opening another row cancels it and
  the ring empties in 200 ms. At 5 s the preview starts and the ring restarts as the countdown. Only
  for `(hover: hover) and (pointer: fine)`; disabled under `prefers-reduced-motion: reduce` (click still
  works). Only one arming at a time.
- **Playback etiquette:** the main track pauses on preview start and resumes on stop (the shell
  already exposes `window.NP_PLAYER`); Escape stops; closing the sheet stops; volume follows
  `window.outputVolume`.

### The look (Aqua/Snow Leopard, the header's own language)

Tokens only — every name below exists in the shell's `:root` today (checked); no new hex values.
- Tile: 30 px stays; the scrim becomes the header's glass — `rgba(255,255,255,.18)` over
  `--srch-art-top/--srch-art-bot` with the existing 1 px inner ring `--srch-art-ring`; the play glyph
  is the transport's own triangle at 12 px, `#fff`, `drop-shadow(0 1px 0 rgba(0,0,0,.35))` like the
  header's embossed text (`--bar-emboss`).
- Ring: 2 px, round caps. **Arming** fills clockwise from 12 in `--lib-accent` (the library's
  selection blue, the same family as the header pill); the **countdown** runs down in `#fff` on
  `rgba(255,255,255,.28)` — two states you can tell apart without reading.
- Focus: the sheet's focus ring is `rgba(24,160,235,.9)`, hard-coded 31 times in the shell today;
  the tile keeps that value for consistency and this pass records it in `design/token-map.json` as
  the candidate for a `--srch-focus` token (not introduced here — one change at a time).
- Row while previewing: `--srch-hot` background plus a 1 px top and bottom hairline in
  `--srch-rule`; the title uses `--srch-ink`.
- Genre chip: the platform-badge style (`.srch__pf`, fill `--srch-pf`, ink `--srch-pf-ink`) with a
  3 px radius, small caps at 10.5 px, `letter-spacing: .02em`.
- Motion: 140 ms ease for reveals (existing), 5 s linear for arming, 200 ms for cancel; nothing
  bounces. Dark values come from the existing dark layer (NPD-002); no new colours.

### Rules, tests, ledger

- New rule `NP-FIND-004 "A listing can be heard before it is added"` (group `np-find`): contract
  as above (click, five-second hold with a visible fill, 30 s, no preview for YouTube and it says so,
  main playback pauses/resumes). `NP-CHROME-001` unchanged. `design/coverage.json`: the search sheet
  entry gains the preview state.
- `np/find.spec.ts`: hub-first ordering when paired (stubbed hub `/search` answering the contract),
  iTunes preview fill-in, the row's feat/album/genre/bpm, click preview 30 s, hold preview (Playwright
  `hover` + clock), cancel on leave, YouTube "no preview", reduced-motion disables hold, main track
  pause/resume. `tests/journey` step 08: search on the real hub returns a row with album + genre +
  bpm for a public-domain fixture track and its click preview plays (the hub's fixture provider).
- Shell edits recorded in `make-shell.py`; `pnpm build:local`; styleguide check/build/pdf.

## Sub-project 3 — BPM measured in the companion

For files that reach the companion without a BPM tag and without a hub answer: a background pass
after each scan, at most one file at a time, lowest priority, cancelled when the app is busy.

- Decode 60 s from the middle of the file to mono 22.05 kHz PCM with ffmpeg (`-ss` mid, `-t 60`,
  `-f s16le`) — only when ffmpeg is present (`tools.ts`); otherwise the pass is skipped and the
  Library view says "Tempo needs ffmpeg" once (NP-PRIN-002).
- Estimate tempo in-process: onset envelope (spectral flux, 1024/512) → autocorrelation over 60–200
  BPM → pick the peak, fold to the 70–180 window, confidence = peak / mean. Pure TypeScript in
  `packages/audio-core/src/tempo.ts`, unit-tested on synthetic clicks at 90/120/174 BPM ± 1 and on
  three real fixture files with known tempos ± 3.
- Result written to the track's `bpm` with `bpmSource: 'analysis'`, `confidence`; pushed to the hub
  on the next sync like any other tag; a later tag or hub answer with higher confidence replaces it.
- Companion Library view shows the tempo column and a small "measured" mark on analysed values.

## Not in scope

Spotify audio features (withdrawn for new apps); key/energy detection (the same analysis pass can grow
it later); rewriting the React `SearchPopover` (not served, DEC-019); Android UI for any of this.

## Order and size

1 → 2 → 3. Sub-project 1 is the largest (≈ 3 adapters, a queue, a migration, contracts, recommender
term, tests). Sub-project 2 is mostly shell CSS/JS via `make-shell.py` plus one spec. Sub-project 3 is
one module plus a scan hook. Each has its own commits; the Hermes prompt is updated after 2 with the
new user-visible checks; the branch is pushed at the end of each sub-project.
